# Changelog

## [Unreleased]

### Added

- Project setup: license, contributing guide, code of conduct, security policy, issue and pull request templates, and CI
- Generator core: schema loader, model builder, naming, and the Rust, Go and TypeScript emitters, driven by `generate(schemas, targets)`
- `idBase` option: every schema `$id` must be `<idBase><file>.json`, with the base derived from the first schema when not given
- `ids` option, like `{ "file": "common", "suffix": "Id" }`, to generate ID types. Off by default
- `examples/basic`: a webhook event, a user and a payment method schema, their generated Rust, Go and TypeScript output, and fixtures that round trip through the Rust and Go output. `pnpm examples` regenerates it and `pnpm examples:check` fails when the committed output is out of date, both through the CLI
- `strictgen.json` config, described by `strictgen.schema.json` (JSON Schema 2020-12). `loadConfig` reads and validates it, applies defaults and resolves paths against the config file's folder, and reports a bad option as a `ConfigError` naming the option path. Only the targets listed under `targets` are generated: Rust (`out`, `fixtures`, `allow`, `embedSchemas`), Go (`out`, `package`, `shared`, `fixtures`) and TypeScript (`out`). Neither Rust nor Go writes a fixture registry unless `fixtures` asks for one. `header` sets the first line of every generated file. Options for later phases (`validation`, `llm`, `docs`) are validated but not yet active
- Before clearing a folder it owns, strictgen checks, with symlinks resolved and case ignored, that the folder holds neither the project, the config file nor the schemas. It never overwrites a hand written file, like a `.gitattributes`, in a shared folder
- `targets.rust.embedSchemas` writes `schemas.rs` with every schema as minified ASCII JSON. Off by default
- `examples/basic/strictgen.json`: the example is generated from its config
- The `strictgen` command line, with a `bin` entry: `strictgen` or `strictgen generate` writes every target, `strictgen check` exits 1 and lists every file that differs, is missing or is stale, without writing, and `strictgen dirs [--json]` prints the folders the targets write to. Every command takes `--config <path>` and `--help`, and `strictgen --version` prints the version. Exit codes: 0 success, 1 generation failed or `check` found a difference, 2 bad usage or a config error
- Formatters: `format.rust` (`rustfmt`, the default, or `none`) and `format.go` (`gofmt`, the default, or `none`) run on the generated files in memory, on stdin, before anything is written. `rustfmt` runs with its defaults and edition 2024, ignoring any `rustfmt.toml`, so `check` gives the same result on every machine. A formatter that isn't installed, or a `rustfmt` whose `--version` fails, is skipped with a notice by `generate` and fails `check`. One that fails, prints nothing, prints something without the generated header, or runs longer than 60 seconds exits 1 with its output, and nothing is written
- `strictgen explain <file.json#/pointer>` prints the model of one type and its declaration in each configured language, formatted like `generate` writes it, or the rule, reason and hint when it can't be generated. `--json` prints the same as JSON. Unknown files and pointers exit 2
- Every generation error carries a stable rule id, like `open-object`, `unsupported-keyword` or `reserved-name`, and a fix hint when there is an obvious one: `user.json#/$defs/address: open-object: objects must be closed, unless only used as an allOf base. Hint: add "additionalProperties": false`. `RULES` lists every id with a summary
- Reserved names per language: a type named like a Rust keyword (`Self`), like a global type the TypeScript output uses (`Record`, `Partial`, `NonNullable`) or a schema file named like a crate the Rust output uses (`serde`, `std`) now fails with `reserved-name` instead of producing code that doesn't compile. Only the configured targets' lists apply. Fields named like keywords stay escaped (`r#match` in Rust)
- A type name that would start with a digit, like one from `$defs/1st`, fails with `unsupported-name`
- `examples/basic/schemas/subscription.json`: a schema whose keys are keywords in Rust, Go or TypeScript (`match`, `async`, `default`, `select`, `self`), with fixtures
- TypeScript decoders, on by default with `targets.typescript.decoders`: `decodeX(json, path?)`, `tryDecodeX(json)` and `encodeX(value)` per type, and a generated `helpers.ts` with `DecodeError` (a JSON Pointer `path` and a `reason`), so there is no package to install. They decode closed objects (unknown keys, missing required keys and `null` for an optional key fail, in schema order like Go), named keys beside a map of the other keys, maps, enums and string, integer and boolean consts (errors list the allowed values), strings, booleans, arrays and aliases. Integers must be whole, within `Number.MAX_SAFE_INTEGER` and not `-0`, and numbers finite. `__proto__` and `constructor` are data keys. Encoders write named keys in schema order, then the other keys sorted by code point. `docs/typescript.md` explains the decoders and what TypeScript can't check about numbers
- `asX(text)` per ID type, a documented cast for strings known to be IDs
- TypeScript decoders for every model kind. Tagged unions read the tag first and decode only that branch; a missing tag, a tag that isn't a string and an unknown tag fail listing the allowed tags, and errors inside a branch name it (`type "card": missing key "last4"`). Nested tagged unions are spread into one, as in Rust and Go. Untagged unions try their variants in the same order as Rust and Go and fail with `data did not match any variant of X`. `{}` decodes any JSON value, null included, and a non-null value anything but `null`. A switch over the model kinds fails to compile when one has no TypeScript decoder or encoder
- TypeScript encoders check what they write and throw an `EncodeError` (with a JSON Pointer `path` and a `reason`) for a value Rust and Go could not hold: an unknown key, a missing required key, a value of the wrong type, an enum value or const the type doesn't list, an enum-keyed map's unlisted key, `NaN` or `Infinity`, and for integers a fraction, `-0` or a value past `Number.MAX_SAFE_INTEGER`. Tagged unions encode the branch the tag names, untagged unions the first variant in decode order that takes the value
- `examples/basic`: a `contact` def in `user.json`, an email or a phone, exactly one, with fixtures that round trip through Rust, Go and TypeScript
- Go enums get a `MarshalText` that fails on a value the type doesn't list, so an unlisted value is never encoded
- `decodeXFromJson(text)` and `tryDecodeXFromJson(text)` per TypeScript type read JSON text with a strict reader in `helpers.ts` instead of `JSON.parse`, and accept and reject the same documents as Rust and Go: a key given twice, data after the value, a lone surrogate, a number out of range, nesting in 128 or more arrays and objects and invalid syntax fail with a `DecodeError` at the JSON Pointer of the value being read, with the offset in UTF-8 bytes. An integer spelled `12.0`, `1e2` or `-0` fails, decided on the text, as in Rust and Go. The reader is bounded by the depth limit, so deep input can't overflow the stack
- TypeScript template literal types for string families: a `pattern` that is a literal prefix or suffix around a part that allows anything, like `^order\..+$`, types the string as `` `order.${string}` ``, for fields, aliases, array items and map keys. Other patterns stay `string`. Rust and Go keep a plain string, and no language checks the pattern yet
- The TypeScript example fixture run reads every fixture from its text with `decodeXFromJson`, with no skips, so all three languages agree on every fixture, duplicate keys included. It skips non-`.json` files and fails on a file outside a `valid` or `invalid` folder, like the Rust and Go harnesses
- One decode error shape in Go and TypeScript, documented in `docs/error-codes.md`: `{ path, code, expected?, found? }` with a fixed list of codes (`unknown_key`, `missing_key`, `null_not_allowed`, `wrong_type`, `bad_tag`, `not_in_enum`, `not_const`, `out_of_range_integer`, `invalid_json`, `duplicate_key`, `too_deep`, and the constraint codes `too_short`, `too_long`, `too_small`, `too_large`, `pattern_mismatch`, `bad_format` and `not_unique` for validation). The message, like `/items/2/price: wrong type, expected a number, found "5"`, and the compact form, like `/items/2/price wrong_type, expected a number, found "5"`, are built from the fields by a rule defined once in the generator, and so are the code titles and how `found` shows a value (strings quoted, escaped and cut to 64 code points, numbers as spelled). Go's `DecodeError` has `Path`, `Code`, `Expected`, `Found`, `Error()` and `Compact()`, and the codes are constants like `CodeUnknownKey`. TypeScript's has `path`, `code`, `expected`, `found`, `message` and `compact()`, and the codes are in `ErrorCode`. Both report the same first error for every example fixture
- Every invalid example fixture has a `<case>.expect.json` with the `path` and `code` it must fail with, which the Go and TypeScript fixture runs check. They fail on an invalid case without one and on an expectation without a case
- `encodeXToJson(value)` per TypeScript type writes JSON text with the keys in the order Rust and Go write them, which `JSON.stringify` can't for keys like `"1"`
- `examples/basic`: a `quota` map in `user.json`, keyed by the `role` enum, with fixtures for an unlisted key, unknown keys and map values in input order, and a long string in an error
- Rust decoders report the shared error shape. Every generated type implements a `Decode` trait, and `T::from_json(text)` (a str or bytes) returns a `DecodeError` with `path`, `code`, `expected` and `found`, a `Display` message and `compact()`, the same as Go and TypeScript for the same input, JSON syntax errors included. The codes are constants like `DecodeError::UNKNOWN_KEY`. The text is read once by a strict reader in the generated `helpers.rs`, then decoded from the parsed tree, so Rust rejects a key given twice anywhere, inside unions and maps too, like Go. Still only `serde` and `serde_json`. `Decode` and `DecodeError` are reserved type names in Rust
- Report read mode: `targets.<lang>.read` is `strict` (the default) or `report`, in Rust, Go and TypeScript. In report mode unknown keys are accepted and every decode collects their JSON Pointers, in input order, the same paths in the same order in every language. One hook receives them (`setUnknownKeyHook` in TypeScript, `SetUnknownKeyHook` in Go, `set_unknown_key_hook` in Rust), and `reportX` / `reportXFromJson` in TypeScript, `Report[X]` and `ReportX` for tagged unions in Go and `X::report_from_json` in Rust return the value with them. Only the branch of an untagged union that decoded reports its keys. Required keys, types, tags, JSON syntax, the keys a sibling branch of an exactly-one union names, and encoders stay strict. `Reported` is reserved in every language, `Report` and `SetUnknownKeyHook` in Go and `UnknownKeyHook` in TypeScript, in both modes. TypeScript's report mode needs `decoders`. Strict output is unchanged. `docs/read-modes.md` documents the mode
- `examples/report`: an order schema generated in report mode, with fixtures whose `<case>.expect.json` lists the unknown key paths a valid case must report, checked by the Rust, Go and TypeScript runs, and in CI
- The Rust fixture run checks each invalid case's `.expect.json` path and code, and fails on an invalid case without one and on an expectation without a case, like Go and TypeScript. `examples/basic/rust/tests/errors.rs` checks the error shape, messages, syntax errors, how strings show in `found` and the key order of enum-keyed maps
- `examples/basic`: invalid event fixtures for an integer spelled `12.0`, `1e2` and `-0`, and an invalid `userId` fixture that starts with a UTF-8 byte order mark, which Rust, Go and TypeScript reject. The TypeScript harness decodes fixture bytes with `ignoreBOM: true`, so the mark reaches the reader

### Changed

- Breaking: generated Rust types no longer implement serde's `Deserialize`. Decode with `T::from_json` from the generated `Decode` trait instead of `serde_json::from_str`; `Serialize` is unchanged. serde's errors had no JSON Pointer or code, and `serde_json` keeps the last of two equal keys in a map or a union
- Rust enums order by their JSON value instead of their variant order, so an enum-keyed map, like `quota` in the example, encodes its keys in code point order, as Go and TypeScript do. Each enum gets `as_str()`
- Rust untagged unions try their variants in order with the strict decoder, like Go and TypeScript, instead of checking the JSON kind first
- The Rust fixture registry's `round_trip` takes bytes and returns a `Failure` with the `DecodeError`
- Generation errors read `<file>#<pointer>: <rule>: <reason>`, with `. Hint: <fix>` when there is one, instead of `<file>#<pointer>: <reason>` with an inline `Fix:`. `CodegenError` has `rule` and `hint` fields
- A key that maps to a Go method or the `Rest` field fails with `reserved-name` instead of reading as a clash between two keys
- TypeScript ID types are branded strings, like `string & { readonly __brand: "UserId" }`, so IDs of different kinds don't mix. `index.ts` re-exports each file with `export *`, plus `DecodeError`, `EncodeError` and `DecodeResult` when decoders are on. A TypeScript type named `DecodeError`, `EncodeError` or `DecodeResult`, or a schema file named `helpers`, fails with `reserved-name`
- The generated example output is formatted with `rustfmt` and `gofmt`. CI checks it with `strictgen check` and installs both formatters
- A getter or Proxy that throws inside a value given to any TypeScript decoder or encoder fails with a `DecodeError` or `EncodeError` at its path, instead of the raw error
- Errors name the place they are about: an unknown key, a missing key, a duplicate key and a tag error are at the key's own path, like `/user/nickname`, and a map key that fails is at its key's path. A JSON syntax error is at the path of the value being read in Go too, not at the root
- Errors inside a tagged union's branch are the branch's own, without the branch name in front. An untagged union no variant takes reports `wrong type, expected <Union>`, and enum and tag errors list the values in the schema's order, quoted, in Go and TypeScript alike
- TypeScript decoders read an object's keys in input order when it came from `decodeXFromJson`, so the first unknown key and the first bad map value are the ones Go reports, keys like `"1"` included
- Go refuses to encode a map key its enum doesn't list in a struct field or an untagged union, which `encoding/json` would write without `MarshalText`
- TypeScript `DecodeError` has `code`, `expected` and `found` instead of `reason`
- Errors while reading schemas or the config, or while writing the output, like a folder where a generated file should go or an `out` path through a symlink that points nowhere, are reported as one line naming the path, never a stack trace

### Removed

- The unused `emitRustRoots`, whose output referenced a module the generator does not write
- `scripts/examples.ts`, replaced by `strictgen check` and `strictgen generate`

### Fixed

- The generated Go JSON parser declares its own error codes in `helpers.go`, `invalid_json`, `duplicate_key` and `too_deep`, so the Go output compiles
