## [Unreleased]

### Added

- Project setup: license, contributing guide, code of conduct, security policy, issue and pull request templates, and CI
- Generator core: schema loader, model builder, naming, and the Rust, Go and TypeScript emitters, driven by `generate(schemas, targets)`
- `idBase` option: every schema `$id` must be `<idBase><file>.json`, with the base derived from the first schema when not given
- `ids` option, like `{ "file": "common", "suffix": "Id" }`, to generate ID types. Off by default
- `examples/basic`: a webhook event, a user and a payment method schema, their generated Rust, Go and TypeScript output, and fixtures that round trip through the Rust and Go output. `pnpm examples` regenerates it and `pnpm examples:check` fails when the committed output is out of date, both through the CLI
- `strictgen.json` config, described by `strictgen.schema.json` (JSON Schema 2020-12). `loadConfig` reads and validates it, applies defaults and resolves paths against the config file's folder, and reports a bad option as a `ConfigError` naming the option path. Only the targets listed under `targets` are generated: Rust (`out`, `fixtures`, `allow`, `embedSchemas`), Go (`out`, `package`, `shared`, `fixtures`) and TypeScript (`out`). Neither Rust nor Go writes a fixture registry unless `fixtures` asks for one. `header` sets the first line of every generated file. Options for later phases (`llm`, `docs`) are validated but not yet active
- Before clearing a folder it owns, strictgen checks, with symlinks resolved and case ignored, that the folder holds neither the project, the config file nor the schemas. It never overwrites a hand written file, like a `.gitattributes`, in a shared folder
- `targets.rust.embedSchemas` writes `schemas.rs` with every schema as minified ASCII JSON. Off by default
- `examples/basic/strictgen.json`: the example is generated from its config
- The `strictgen` command line, with a `bin` entry: `strictgen` or `strictgen generate` writes every target, `strictgen check` exits 1 and lists every file that differs, is missing or is stale, without writing, and `strictgen dirs [--json]` prints the folders the targets write to. Every command takes `--config <path>` and `--help`, and `strictgen --version` prints the version. Exit codes: 0 success, 1 generation failed or `check` found a difference, 2 bad usage or a config error
- Formatters: `format.rust` (`rustfmt`, the default, or `none`) and `format.go` (`gofmt`, the default, or `none`) run on the generated files in memory, on stdin, before anything is written. `rustfmt` runs with its defaults and edition 2024, ignoring any `rustfmt.toml`, so `check` gives the same result on every machine. A formatter that isn't installed, or a `rustfmt` whose `--version` fails, is skipped with a notice by `generate` and fails `check`. One that fails, prints nothing, prints something without the generated header, or runs longer than 60 seconds exits 1 with its output, and nothing is written
- `strictgen explain <file.json#/pointer>` prints the model of one type and its declaration in each configured language, formatted like `generate` writes it, or the rule, reason and hint when it can't be generated. `--json` prints the same as JSON. Unknown files and pointers exit 2
- Every generation error carries a stable rule id, like `open-object`, `unsupported-keyword` or `reserved-name`, and a fix hint when there is an obvious one: `user.json#/$defs/address: open-object: objects must be closed, unless only used as an allOf base. Hint: add "additionalProperties": false`. `RULES` lists every id with a summary
- Reserved names per language: a type named like a Rust keyword (`Self`), like a global type the TypeScript output uses (`Record`, `Partial`, `NonNullable`) or a schema file named like a crate the Rust output uses (`serde`, `std`) now fails with `reserved-name` instead of producing code that doesn't compile. Only the configured targets' lists apply. Fields named like keywords stay escaped (`r#match` in Rust)
- A type name that would start with a digit, like one from `$defs/1st`, fails with `unsupported-name`
- `examples/basic/schemas/subscription.json`: a schema whose keys are keywords in Rust, Go or TypeScript (`match`, `async`, `default`, `select`, `self`), with fixtures
- TypeScript decoders, on by default with `targets.typescript.decoders`: `decodeX(json, path?)`, `tryDecodeX(json)` and `encodeX(value)` per type, and a generated `helpers.ts` with `DecodeError` (a JSON Pointer `path` and a `reason`), so there is no package to install. They decode closed objects (unknown keys, missing required keys and `null` for an optional key fail, in schema order like Go), named keys beside a map of the other keys, maps, enums and string, integer and boolean consts (errors list the allowed values), strings, booleans, arrays and aliases. Integers must be whole, within `Number.MAX_SAFE_INTEGER` and not `-0`, and numbers finite. `__proto__` and `constructor` are data keys. Encoders write named keys in schema order, then the other keys sorted by code point. `docs/typescript.md` explains the decoders and what TypeScript can't check about numbers
- `asX(text)` per ID type, a documented cast for strings known to be IDs
- TypeScript decoders for every model kind. Tagged unions read the tag first and decode only that branch; a missing tag, a tag that isn't a string and an unknown tag fail listing the allowed tags, and errors inside a branch name it (`type "card": missing key "last4"`). Nested tagged unions are spread into one, as in Rust and Go. Untagged unions try their variants in the same order as Rust and Go and fail with `data did not match any variant of X`. `{}` decodes any JSON value, null included, and a non-null value anything but `null`. A switch over the model kinds fails to compile when one has no TypeScript decoder or encoder
- TypeScript encoders check what they write and throw an `EncodeError` (with a JSON Pointer `path` and a `reason`) for a value Rust and Go could not hold: an unknown key, a missing required key, a value of the wrong type, an enum value or const the type doesn't list, an enum-keyed map's unlisted key, `NaN` or `Infinity`, and for integers a fraction, `-0` or a value past `Number.MAX_SAFE_INTEGER`. Tagged unions encode the branch the tag names, untagged unions the first variant in decode order that takes the value
- `examples/basic`: a `contact` def in `user.json`, an email or a phone, exactly one, with fixtures that round trip through Rust, Go and TypeScript
- Go enums get a `MarshalText` that fails on a value the type doesn't list, so an unlisted value is never encoded
- `decodeXFromJson(text)` and `tryDecodeXFromJson(text)` per TypeScript type read JSON text with a strict reader in `helpers.ts` instead of `JSON.parse`, and accept and reject the same documents as Rust and Go: a key given twice, data after the value, a lone surrogate, a number out of range, nesting in 128 or more arrays and objects and invalid syntax fail with a `DecodeError` at the JSON Pointer of the value being read, with the offset in UTF-8 bytes. An integer spelled `12.0`, `1e2` or `-0` fails, decided on the text, as in Rust and Go. The reader is bounded by the depth limit, so deep input can't overflow the stack
- TypeScript template literal types for string families: a `pattern` that is a literal prefix or suffix around a part that allows anything, like `^order\..+$`, types the string as `` `order.${string}` ``, for fields, aliases, array items and map keys. Other patterns stay `string`. Rust and Go keep a plain string, and no language checks the pattern yet
- The TypeScript example fixture run reads every fixture from its text with `decodeXFromJson`, with no skips, so all three languages agree on every fixture, duplicate keys included. It skips non-`.json` files and fails on a file outside a `valid` or `invalid` folder, like the Rust and Go harnesses
- One decode error shape in Go and TypeScript, documented in `docs/error-codes.md`: `{ path, code, expected?, found? }` with a fixed list of codes (`unknown_key`, `missing_key`, `null_not_allowed`, `wrong_type`, `bad_tag`, `not_in_enum`, `not_const`, `out_of_range_integer`, `invalid_json`, `duplicate_key`, `too_deep`, and the constraint codes `too_short`, `too_long`, `too_small`, `too_large`, `pattern_mismatch`, `bad_format` and `not_unique` for validation). The message, like `/items/2/price: wrong type, expected a number, found "5"`, and the compact form, like `/items/2/price wrong_type, expected a number, found "5"`, are built from the fields by a rule defined once in the generator, and so are the code titles and how `found` shows a value (strings quoted, escaped and cut to 64 code points, numbers as spelled). Go's `DecodeError` has `Path`, `Code`, `Expected`, `Found`, `Error()` and `Compact()`, and the codes are constants like `CodeUnknownKey`. TypeScript's has `path`, `code`, `expected`, `found`, `message` and `compact()`, and the codes are in `ErrorCode`. Both report the same first error for every example fixture
- Every invalid example fixture has a `<case>.expect.json` with the `path` and `code` it must fail with, which the Go and TypeScript fixture runs check. They fail on an invalid case without one and on an expectation without a case
- `encodeXToJson(value)` per TypeScript type writes JSON text with the keys in the order Rust and Go write them, which `JSON.stringify` can't for keys like `"1"`
- `examples/basic`: a `quota` map in `user.json`, keyed by the `role` enum, with fixtures for an unlisted key, unknown keys and map values in input order, and a long string in an error
- Rust decoders report the shared error shape. Every generated type implements a `Decode` trait, and `T::from_json(text)` (a str or bytes) returns a `DecodeError` with `path`, `code`, `expected` and `found`, a `Display` message and `compact()`, the same as Go and TypeScript for the same input, JSON syntax errors included. The codes are constants like `DecodeError::UNKNOWN_KEY`. The text is read once by a strict reader in the generated `helpers.rs`, then decoded from the parsed tree, so Rust rejects a key given twice anywhere, inside unions and maps too, like Go. Still only `serde` and `serde_json`. `Decode` and `DecodeError` are reserved type names in Rust
- Report read mode: `targets.<lang>.read` is `strict` (the default) or `report`, in Rust, Go and TypeScript. In report mode unknown keys are accepted and every decode collects their JSON Pointers, in input order, the same paths in the same order in every language. One hook receives them (`setUnknownKeyHook` in TypeScript, `SetUnknownKeyHook` in Go, `set_unknown_key_hook` in Rust), and `reportX` / `reportXFromJson` in TypeScript, `Report[X]` and `ReportX` for tagged unions in Go and `X::report_from_json` in Rust return the value with them. Only the branch of an untagged union that decoded reports its keys. Required keys, types, tags, JSON syntax, the keys a sibling branch of an exactly-one union names, and encoders stay strict. `Reported` is reserved in every language, `Report` and `SetUnknownKeyHook` in Go and `UnknownKeyHook` in TypeScript, in both modes. TypeScript's report mode needs `decoders`. Strict output is unchanged. `docs/read-modes.md` documents the mode
- `examples/report`: an order schema generated in report mode, with fixtures whose `<case>.expect.json` lists the unknown key paths a valid case must report, checked by the Rust, Go and TypeScript runs, and in CI
- The Rust fixture run checks each invalid case's `.expect.json` path and code, and fails on an invalid case without one and on an expectation without a case, like Go and TypeScript. `examples/basic/rust/tests/errors.rs` checks the error shape, messages, syntax errors, how strings show in `found` and the key order of enum-keyed maps
- `examples/basic`: invalid event fixtures for an integer spelled `12.0`, `1e2` and `-0`, and an invalid `userId` fixture that starts with a UTF-8 byte order mark, which Rust, Go and TypeScript reject. The TypeScript harness decodes fixture bytes with `ignoreBOM: true`, so the mark reaches the reader
- Validation: `minLength` and `maxLength` on strings, counted in Unicode code points in every language (TypeScript doesn't use `.length`), `minimum`, `exclusiveMinimum`, `maximum` and `exclusiveMaximum` on integers and numbers, `multipleOf` on integers, `minItems` and `maxItems` on arrays, and `minProperties` and `maxProperties` on maps are checked by the Rust, Go and TypeScript decoders, on map keys and ids too. They fail with `too_short`, `too_long`, `too_small`, `too_large` and the new code `not_multiple_of`, with the same `expected` and `found` in every language, like `/note: too long, expected at most 5 characters, found 6 characters` and `/price: too large, expected < 1000, found 1000`. Constraints are checked once the whole value has decoded, so a structure error anywhere comes first, then in one fixed order documented in `docs/error-codes.md`: a value's own constraints before the values inside it, fields in schema order, items by index and map keys in code point order. Integers compare exactly, numbers as the nearest 64-bit float. `validation: false` leaves the checks out of every decoder
- Generation fails, with a rule id and a hint, on a constraint that can't be checked the same way everywhere: `multipleOf` on a number (`unsupported-constraint`), a constraint beside a type it doesn't apply to, like `maxLength` on an integer, beside `$ref`, `enum` or `const`, or key counts on an object with named properties (`misplaced-keyword`), and a bad value, like a negative `minLength`, an integer bound that isn't a safe integer, a boolean `exclusiveMinimum` or limits that leave no value (`invalid-constraint`). `contains` is no longer accepted (`unsupported-keyword`)
- Rust: `Decode::from_json` checks the constraints after decoding, through a `check` method generated for each type that has some. Go: `UnmarshalJSON`, `Report[X]` and the `DecodeX` functions of tagged unions do the same through a `check` method. TypeScript: `decodeX` decodes types with constraints through `h.checked`. Every standard entry point checks, so there is no separate checking function
- Validation of `pattern`, `format` and `uniqueItems` in Rust, Go and TypeScript, with the codes `pattern_mismatch`, `bad_format` and `not_unique`, like `/tracking: pattern mismatch, expected matching ^[A-Z]{2}\d{9}[A-Z]{2}$, found "AB12345678US"`, `/shippedAt: bad format, expected a date-time, found "2024-01-02 03:04:05Z"` and `/labels/2: not unique, expected unique items, found a repeat of item 0`. A string's `pattern` and `format` follow `maxLength`, and an array's `uniqueItems` follows `maxItems` and comes before its items. `docs/error-codes.md` documents each rule
- `pattern` is read as ECMAScript with the `u` flag and unanchored, as JSON Schema says, then rewritten into one portable form that Rust's `regex` crate, Go's RE2 and ECMAScript read the same way: `\d` and `\w` are ASCII, `\s` is ECMAScript's white space, `.` doesn't match `\r`, U+2028 or U+2029, and classes are written as sorted ranges with Rust's class syntax escaped. Each language compiles every pattern once. Lookarounds, backreferences, named groups, word boundaries, Unicode property escapes, inline flags, repeats above 1000, patterns above 100,000 steps once their repeats are written out (Rust's `regex` refuses a compiled pattern above 10 MiB) and patterns of more than 2000 parts (V8 fails on a few thousand when its stack is small) fail generation with `unsupported-pattern`, the reason and the character it is at, so every accepted pattern compiles in all three languages. Generated Rust uses the `regex` crate only when a schema has a `pattern`; add `regex = "1.10"` to the crate then
- `format` checks `date-time` and `date` (RFC 3339, with lower case `t` and `z`, offsets including `-00:00` and leap seconds only at 23:59:60 UTC) and `uuid` (RFC 9562 text form, either case, any version) with one hand-written grammar per format in each language, no regex or date library. Any other format fails generation with `unsupported-format`
- `uniqueItems: true` compares the decoded items by their RFC 8785 canonical JSON, so `1` and `1.0` are equal and key order doesn't matter, and fails at the later of two equal items
- `examples/basic`: `shipment.json`, with patterns, formats and unique items, and fixtures for every edge case: unanchored patterns, `.`, `\s`, `\w` and `\d` on characters the engines read differently, `$` before a line feed, code points outside the BMP, leap years and leap seconds, offsets, UUID case, number spellings, key order and `-0` in unique items, and the check order. `examples/report` gets a pattern, a date-time and a list of unique items, with a fixture whose items differ only in unknown keys
- The Go fixture registry has `fixtureTypes()`, a new value of each fixture folder's type, and both Go examples decode every such fixture with `json.Unmarshal` too and check it gives what the registry gives
- CI runs `cargo clippy` with the pedantic lints, as errors, on both Rust examples, generated code and hand written tests alike
- `examples/basic`: `order.json`, with a limit of every kind, an `orderId` with a length range in `common.json`, and fixtures at, just below and just above each limit, with emoji and combining marks for lengths, which Rust, Go and TypeScript agree on. `examples/report` gets a length, a minimum and a `tags` def, a list with limits, with fixtures for a constraint beside unknown keys and inside an untagged branch, since report mode checks constraints the same way
- `strictgen fix [--write]` rewrites schemas into the supported subset with rules that run until nothing changes: `close-objects` closes open objects, `tag-unions` makes a `oneOf` whose branches each have a `const` property a tagged union, `merge-allof` inlines `allOf` parts that don't disagree, and `hoist-defs` moves `definitions`, nested `$defs` and schemas a `$ref` points into into `$defs` with generated names, rewriting every `$ref` to them. It prints a unified diff, or writes in place with `--write`, keeping each file's key order, number spelling, string escapes, indentation, line endings and the formatting of untouched parts. Then it generates every target in memory and lists what is left to change by hand, with file, JSON pointer, rule and hint, and exits 1 when generation still fails. `fixSchemas` in the package does the same in memory
- `strictgen breaking --base <ref or folder>` compares the schemas with an older version on the model, so renamed defs and internal names don't show, and lists each change with its JSON pointer in both versions and who it breaks: all consumers, strict consumers, producers, or nobody. Added optional fields are safe when every target reads in report mode. Constraint changes are decided per keyword, and a changed `pattern` breaks both ways. A ref is read with `ls-tree` and `cat-file`, with the config at that ref, and nothing is checked out. Text output, or `--json` for CI; exit 1 when anything breaks, 2 when the base can't be loaded or has no schemas. `docs/breaking-changes.md` has the rule table
- LLM provider profiles: `openai`, `anthropic` and `gemini` ship as versioned data files in `profiles/`, each listing the keywords, formats and limits of the provider's structured output schemas and the sources they come from, validated against `profiles/profile.schema.json`. A path ending in `.json` in `llm.profiles` loads a profile file, which replaces the built in profile of its name
- `llm.out` writes a provider-ready schema per type and profile, `<out>/<profile>/<Type>.json`, projected from the real schema: every object closed and every field required, optional fields nullable, tagged unions as `anyOf` with a `const` tag, roots that aren't objects wrapped as `{ "value": ... }`, maps as `{ key, value }` entries or objects, and constraints a profile doesn't take left out with a fixed hint in the description. A type over a profile limit fails with `llm-limit`, and one no provider schema can describe (any JSON value, data keys beside properties, recursion without profile support) with `llm-unsupported`, both naming the schema path. Limits count each `$defs` entry at every place it is used, and a recursive type under a `maxDepth` fails, since its nesting has no bound. `check` compares the folder, `dirs` lists it, and strictgen clears it before writing
- `strictgen llm --profile <name> <Type> [--json]` prints one provider-ready schema on stdout and what moved to the decoder on stderr
- `llm.cleanup` adds `cleanLlmJson` (TypeScript), `CleanLLMJSON` (Go) and `clean_llm_json` (Rust): they remove a byte order mark at the start, white space at both ends, a code fence around the whole text and trailing commas outside strings, and nothing else. `docs/llm.md` spells out the algorithm, and `examples/llm` runs one set of vectors through all three
- LLM decoders for every type with a provider-ready schema: `decodeXFromLlm` and `tryDecodeXFromLlm` (TypeScript), `DecodeXFromLlm` (Go) and `decode_x_from_llm` (Rust). They read the JSON text a model sent, run the cleanup step first when `llm.cleanup` is on, read `null` as absent for optional fields, unwrap `{ "value": ... }` for types that aren't objects, read maps as `{ key, value }` entries or objects as the configured profiles give them (a key given twice fails with `duplicate_key`), and then check every constraint of the real type. Errors have the shared shape with paths in the model's payload, and LLM decoders are strict in every read mode. An untagged union with a map beside an array fails with `llm-unsupported` for a profile that gives maps as entries. `examples/llm/llm-vectors.json` holds the payloads every language is tested on, written by `pnpm vectors:llm`

- A deterministic payload generator, `PayloadGenerator`, shared by `strictgen examples`, `strictgen docs` and the fuzzer to come. For a seed it makes valid payloads for any type that keep every rule of the model (closed objects, required keys, tags, the order of untagged unions, enums, consts, map key types, ids) and every constraint (lengths in code points, bounds, `multipleOf`, item and key counts, unique items, patterns and formats), with recursion bounded by a depth. Near misses change one thing in a valid payload and carry the `{ path, code }` error every decoder reports: a missing or unknown key, `null`, another JSON type, a wrong tag, enum value or const, a number just past a bound, a string, array or map one past its limit, a repeated item, and text with `<`, `>` and `&` where a pattern or a format doesn't take it. Inside an untagged union the label is the union's own error, and a change another variant takes is left out. A type it can't make a sure value for, like a pattern it can't match within the length limits, fails with a `GenerateError` rather than give a payload that may be invalid
- `strictgen examples <type>` prints valid payloads of a type, one per line, or with `--invalid` near misses as `{ path, code, change, payload }`. `--count`, `--seed` and `--array` (one JSON array). The same seed gives the same output, and payloads hold in the read mode of every configured target
- `strictgen docs` writes a Markdown page per type and `index.md` into `docs.out`: the description, where the schema defines it, its type in each configured language, fields, values, branches or variants, constraints, a valid example and links to the types it uses and that use it. `docs.format: "html"` or `--format html` writes one self-contained `index.html` with an anchor per type instead. All schema text is escaped. The docs folder is shared: only files that start with the header, as an HTML comment, are replaced or removed, and `docs.out` can't be a target folder or sit inside an owned one
- The conformance suite, `pnpm conformance`: schemas in `conformance/schemas`, cases in `conformance/cases/<Type>/{valid,invalid}`, each invalid case with the first error it must give in `<case>.expect.json`, and `report` when report mode reads it differently, and `conformance/manifest.json` with the case counts of every type, so a case that disappears fails the run. The runner generates every language into a temporary folder, builds one Rust and one Go driver that each read a batch of cases over stdin, runs TypeScript in process, and compares, in strict and report mode and through both the public entry points (`json.Unmarshal`, `Report[T]`, `from_json`, `report_from_json`, `decodeXFromJson`, `reportXFromJson`) and the fixture registry: accept or reject, the first error (path, code, expected, found and message), the unknown key paths, the re-encoded bytes after RFC 8785 canonicalisation, and the bytes as written. Disagreements print as a table and exit 1. Known differences, like TypeScript integers past 2^53 - 1 or Go escaping U+2028, are marked in `conformance/marks.json` with a reason, and every mark must still be needed. `pnpm test` runs every case through TypeScript, and CI runs the whole suite with Rust and Go and lints the drivers. The example fixtures moved into it; the examples keep a few for their own tests
- The conformance suite covers every mapping rule and error code, and the LLM decoders. Each mapping rule has a stable id (`object`, `tagged`, `map.key`, `string.pattern`, `integer.int64`, ...), and which rules a case covers is worked out from the case and the model, never tagged by hand: a valid case covers what its value is read through, an invalid case the construct its expected error is at. A rule without a valid or an invalid case, or an error code without a case, fails the run and `pnpm test`, unless `manifest.json`'s `coverage` gives the reason it can't have one (`any/invalid`). `pnpm conformance --coverage` prints the counts. New schemas `bundle.json` (consts, a recursive part, values of any JSON type, nesting at and past the depth limit) and `refund.json` (an enum-keyed map and an untagged union whose branches share an optional key, all of it projectable), with cases written by `scripts/conformance-cases.mjs`
- Every case also runs through the LLM decoders of Rust, Go and TypeScript, in the form a model sends: null for an absent optional key, a type that isn't a struct wrapped as `{"value": ...}`, and maps as entries or as objects. The decoders come from code generated with profiles that give both map shapes (in strict and report mode), entries only and objects only; the normal decoders of that code run too. A valid case's LLM decode must encode to the same canonical bytes as the case itself, an invalid case must give its strict error at the path in the payload, and near misses only the LLM form has (the object around a wrapped type, broken entries, a key given twice, a payload cut short, a map in the shape the decoder doesn't read) carry their own expectations. Schema files no provider-ready schema can describe are listed in `manifest.json`'s `llm` with the reason, and must be. The shared LLM vectors and cleanup vectors of `examples/llm` run in report mode in all three languages
- Emitters given an `llm` option that reads maps in no shape fail instead of writing decoders that read null for absent nowhere
- The differential fuzzer, `pnpm fuzz --seed s --runs n`: each run makes a valid payload of a random conformance type, near misses of it with the error the payload generator labels them with, an unknown key and a cleanup input, and runs them through every decoder of the suite in Rust, Go and TypeScript, the LLM decoders included, in batches through the same drivers. Any disagreement in the result, the five error fields, the unknown keys or the bytes, or with a label, fails the run and prints the seed, the run, the payload as JSON and hex, and the table. The payload is then shrunk, keys, items and characters removed and numbers simplified while the same fields disagree, and `--save <language>` writes it into `conformance/cases` with that language's answer as the expectation and updates `manifest.json`. Every pull request runs a fixed seed in CI, and a nightly run with a random seed opens an issue with the seed and the shrunk case
- `targets.rust.serdeBridge` (off by default) gives every generated Rust type that implements `Decode` serde's `Deserialize`: it takes the value's raw JSON text from serde_json (its `raw_value` feature) and decodes it with `from_json`, so a generated type can sit inside your own serde types and stay strict. A strict error becomes a serde error whose message is the compact form, with the path relative to the value. Plain type aliases get no impl. With the option off, the output is unchanged. `examples/basic` turns it on, and the conformance suite runs every case through it as the `serde` entry; `docs/serde-bridge.md` explains when to use it
- The playground, `playground/`: a static page that runs the real generator and the generated TypeScript decoders in the browser, with no server. It shows the Rust, Go, TypeScript and LLM output of pasted schemas side by side, unformatted, and decodes a payload as a picked type in strict or report mode or through the LLM decoder, showing accept, reject with the shared error and its compact form, or the unknown keys. The state is kept in the URL fragment, compressed, so a link shares it. Decoders run in a Web Worker that is stopped after 5 seconds. `pnpm playground:build` bundles it with esbuild into `playground/dist` and fails when the generator code it pulls in imports a Node built in module; `pnpm playground:serve` serves it on 127.0.0.1. `generateInMemory` in `src/memory.ts` is the generator without a file system, and gives the CLI's output byte for byte before formatting
- User docs: a README with a 30 second example, and `docs/cli.md`, `docs/schemas.md` (the subset, and every generation rule with an example and its fix), `docs/mapping.md` (every construct per language), per-code examples in `docs/error-codes.md`, per-profile tables and a worked example in `docs/llm.md`, and `docs/comparison.md`
- `examples/quickstart`: one schema, its generated code and a decoding program in Rust, Go and TypeScript, and `examples/fix`, a schema for `strictgen fix`
- `pnpm docs` writes every snippet of the README and docs from real output, the error lines from running the Rust, Go and TypeScript decoders, and `pnpm docs:check` fails in CI when one is out of date
- Single binaries for macOS (arm64, x64), Linux (x64, arm64) and Windows (x64), built as Node single executable applications with the built in profiles embedded, so Rust and Go projects don't need Node. CI builds each on its own platform and checks it against `node dist/cli.js`: the same `--version`, `--help` and `llm --profile openai` output, `check` on two examples, and byte-identical `generate` output on every example
- The npm package: `bin`, `exports` (the API from `dist/index.js` with its types), `files` (only the CLI and API modules, `profiles/`, `strictgen.schema.json` so a config's `$schema` can point into `node_modules`, and the docs files; not the conformance runner or docs tools), `publishConfig.provenance` and a `prepublishOnly` guard that stops `npm publish` outside the release workflow's tag run. CI checks the exact file list and installs the tarball offline to run it
- A release workflow: a `v<version>` tag publishes to npm with provenance and creates a GitHub release with the binaries, `SHA256SUMS` and the changelog section, only from a public repository with `NPM_TOKEN` set, after checking the tag, the changelog and all of CI. Run by hand with `dry_run`, it builds everything and publishes nothing. The versioning policy is in `CONTRIBUTING.md`
- Go: each generated package has `Encode(v any) ([]byte, error)`, which writes a value as JSON with the same bytes as Rust and TypeScript: `<`, `>`, `&`, U+2028 and U+2029 as they are, and the strings inside a value of any JSON type with the same escapes as any other string. `json.Marshal` still works and writes the same JSON value, escaped the way `encoding/json` does. `Encode` is a reserved type name in Go

### Changed

- The conformance runner runs the generated TypeScript in a Node process of its own, like the Rust and Go drivers, so a decoder that never returns stops the run with a timeout instead of hanging it
- An invalid conformance case whose error a null for an optional key causes, like a null that keeps every branch of an untagged union from taking the value, no longer runs through the LLM decoders, which read that null as absent
- The payload generator's `multipleOf` near misses include values on both sides of zero where the range takes them, and the conformance `Order` has a field (`adjustment`) whose range crosses zero; the shared LLM vectors of `examples/llm` gain those near misses
- CI caches the Rust and Go builds of the conformance drivers and the examples
- Breaking: in Go, every def that isn't a `$ref` to another def is a defined type, like `type Tags []string`, `type Name string` or `type Amount json.Number`, instead of a Go alias, with an `UnmarshalJSON` that reads with the strict parser. Before, `json.Unmarshal` into an alias without constraints went through `encoding/json`, so a number alias took `1e400` and a map alias a key given twice, which Rust and TypeScript reject. Now every public Go entry point on every root type accepts and rejects what Rust and TypeScript do. Code that passed a value of the underlying named type converts it, like `Name(s)`. Aliases of any JSON, a non-null value or a const forward `MarshalJSON` to the type they stand for. An alias of another def stays a Go alias
- Breaking: a `not` beside a string, like `{ "type": "string", "not": { "enum": ["admin"] } }`, fails generation with `unsupported-not`, since no decoder checked it. Use `pattern` or an `enum` of the allowed values instead
- Breaking: schema parts that generated but that no decoder checked now fail generation, so a schema that used one and generated before fails until it is changed. `anyOf` beside properties, like "at least one of `email` or `phone`", fails with `misplaced-keyword`: before, `{}` decoded. Use `oneOf` for exactly one of the keys, or list them in `required`. `if`, `then` and `else` fail with `unsupported-keyword` in every schema strictgen reads, `allOf` parts and bases and the schema inside `not` included: before, the condition was ignored, and array `items` given only in `then` branches became one union for every case. Use a tagged union. `unevaluatedProperties` in an `allOf` part, or other than `false` in an `allOf` base, fails with `misplaced-keyword`, a `type` beside `$ref` that isn't the def's own with `type-mismatch`, and a key set to `false` beside `$ref` that the def can hold with `ref-siblings`. A named key that `propertyNames` doesn't allow, like `default` beside `"propertyNames": { "type": "string", "maxLength": 3 }`, fails with `invalid-constraint`, since JSON Schema applies `propertyNames` to it too. The `const` branches of a `propertyNames` `anyOf`, `allOf` bases and the schema inside `not` get the same keyword checks as every other schema. A union that is one of its own branches fails with `ref-cycle` instead of a stack overflow
- Generated output changes for a schema with `pattern` or `format`: a def with one is a type of its own in Rust, like `pub struct Timestamp(pub String)` for `common.json`'s `timestamp`, and the types that hold one get a check. With `validation: false` neither is checked, and `format` is left out of the model
- Breaking: a def with constraints that stands for a type that can't check them, like a list of at most two codes or a string of 3 characters, is a type of its own in Rust and Go instead of an alias: a newtype in Rust, like `pub struct Codes(pub Vec<Code>)` with `#[serde(transparent)]`, and a defined type in Go, like `type Codes []Code`, with `UnmarshalJSON` and a `check` method. So `Codes::from_json`, `Codes::report_from_json`, `json.Unmarshal` into `Codes` and `Report[Codes]` check its constraints, and so does every type that holds one. Code that built such a value from the type it stands for wraps or converts it, like `Codes(vec![...])` or `Codes(list)`. A newtype of a string is ordered, so it can key a map. A def that only refers to another type, or in Rust has no constraints, stays an alias. TypeScript output is unchanged
- Breaking: generated Rust types no longer implement serde's `Deserialize`. Decode with `T::from_json` from the generated `Decode` trait instead of `serde_json::from_str`; `Serialize` is unchanged. serde's errors had no JSON Pointer or code, and `serde_json` keeps the last of two equal keys in a map or a union
- Rust enums order by their JSON value instead of their variant order, so an enum-keyed map, like `quota` in the example, encodes its keys in code point order, as Go and TypeScript do. Each enum gets `as_str()`
- Rust untagged unions try their variants in order with the strict decoder, like Go and TypeScript, instead of checking the JSON kind first
- The Rust fixture registry's `round_trip` takes bytes and returns a `Failure` with the `DecodeError`
- Generation errors read `<file>#<pointer>: <rule>: <reason>`, with `. Hint: <fix>` when there is one, instead of `<file>#<pointer>: <reason>` with an inline `Fix:`. `CodegenError` has `rule` and `hint` fields
- A key that maps to a Go method or the `Rest` field fails with `reserved-name` instead of reading as a clash between two keys
- TypeScript ID types are branded strings, like `string & { readonly __brand: "UserId" }`, so IDs of different kinds don't mix. `index.ts` re-exports each file with `export *`, plus `DecodeError`, `EncodeError` and `DecodeResult` when decoders are on. A TypeScript type named `DecodeError`, `EncodeError` or `DecodeResult`, or a schema file named `helpers`, fails with `reserved-name`
- The generated example output is formatted with `rustfmt` and `gofmt`. CI checks it with `strictgen check` and installs both formatters
- A getter or Proxy that throws inside a value given to any TypeScript decoder or encoder fails with a `DecodeError` or `EncodeError` at its path, instead of the raw error
- Errors name the place they are about: an unknown key, a missing key, a duplicate key and a tag error are at the key's own path, like `/user/nickname`, and a map key that fails is at its key's path. A JSON syntax error is at the path of the value being read in Go too, not at the root
- Errors inside a tagged union's branch are the branch's own, without the branch name in front. An untagged union no variant takes reports `wrong type, expected <Union>`, and enum and tag errors list the values in the schema's order, quoted, in Go and TypeScript alike
- TypeScript decoders read an object's keys in input order when it came from `decodeXFromJson`, so the first unknown key and the first bad map value are the ones Go reports, keys like `"1"` included
- Go refuses to encode a map key its enum doesn't list in a struct field or an untagged union, which `encoding/json` would write without `MarshalText`
- TypeScript `DecodeError` has `code`, `expected` and `found` instead of `reason`
- Rust reads a number that isn't an integer with Rust's own float parser, which rounds correctly, instead of serde_json's default one, which can be a step off for long numbers, so Rust compares the same value as Go and TypeScript. The example crate turns on serde_json's `float_roundtrip` feature, so its fixture run compares exact values too
- Generated output changes for a schema with constraints, which were ignored before: types with constraints get a check, and the helpers the checks call
- Errors while reading schemas or the config, or while writing the output, like a folder where a generated file should go or an `out` path through a symlink that points nowhere, are reported as one line naming the path, never a stack trace

### Removed

- The unused `emitRustRoots`, whose output referenced a module the generator does not write
- `scripts/examples.ts`, replaced by `strictgen check` and `strictgen generate`

### Fixed

- Generated Go wrote `<`, `>` and `&` as `\u003c`, `\u003e` and `\u0026`, and U+2028 and U+2029 escaped, where Rust and TypeScript write the characters, so a hash of the bytes each language wrote differed. A value of any JSON type was written with the escapes of its input. Go code that wants the same bytes now encodes with the generated `Encode`; the generated Go output changes by that function in `helpers.go`. The conformance suite no longer allows these differences: the `html-escaping`, `line-separator-escaping` and `string-escaping` marks are gone, and raw bytes must match for every case they covered
- On Windows, `strictgen generate` and `check` failed on every Rust file: rustfmt was given the null device as its config path and refused it ("unable to find a config file for the given path"). It now gets an empty `rustfmt.toml` in a temporary folder, on every platform. This affected the npm package on Windows too, not only the binary
- The test that runs the built command with its output closed compiled the command inside the test, which flaked once under load. It compiles once in a hook with its own timeout
- The generated Go JSON parser declares its own error codes in `helpers.go`, `invalid_json`, `duplicate_key` and `too_deep`, so the Go output compiles
- A pattern of many large repeats in a row, like eight `.{1000}`, passed generation and Go, but Rust's `regex` refused to compile it and every pattern check panicked. Generation now bounds the written-out size of a pattern, and the generated Rust sets the `regex` size limit itself
- Go string literals for enum values, consts, tags and keys were written with `JSON.stringify`, so a value holding a byte order mark or NUL gave Go that doesn't compile. Every string literal strictgen writes, in Rust, Go and TypeScript, is now printable ASCII with escapes, and comments write control characters, line separators, the byte order mark, bidi controls and lone surrogates as `\u{...}` text. `examples/basic/schemas/marks.json` has enum values, consts and tags with each of them, with fixtures that round trip in all three languages
